# reva.link revamp plan

## Current state

- Hugo site in `docs/`, Docsy theme as a git submodule (pinned 2024), npm and postcss for the theme.
- The site does not build with a current Hugo (0.160): Docsy uses `.Site.Author`, which Hugo removed. Netlify pins Hugo 0.142.
- `make gen-doc` runs `cato`. It writes config references for 50 of 342 packages into `docs/autogenerated/`.
- `ADOPTERS.md` lists no adopters. The about page has the history in prose.
- HTTP services declare routes with `router.Describe`. The `openapi` service serves the spec and Swagger UI at `/openapi`.

## Goals

1. Documentation pages per component, generated from the code.
2. Swagger UI for the HTTP API, with the spec of the CERNBox deployment.
3. Clickable architecture diagram on the home page.
4. History page.
5. Deployments page.
6. Quick start guide that is tested by running it.
7. Contributors page.
8. Other additions (see "Extras").

## Decisions

### D1. Replace Docsy with a small custom theme

- Docsy needs a submodule, npm, postcss, and Bootstrap. It is broken on current Hugo.
- A custom theme in `docs/layouts` and `docs/assets` needs only Hugo. No Node, no submodule.
- Full control over the home page, the diagram, and the component pages.
- Cost: I must write the sidebar, mobile menu, search, and dark mode myself. This is a few hundred lines of HTML, CSS, and JS.
- Remove: `docs/themes/docsy` submodule, `package.json`, `package-lock.json`, `node_modules`, `go.mod` (Hugo modules for Docsy).
- Netlify: `hugo --gc --minify`, Hugo 0.160.1.

### D2. One generator, output committed

- Extend `tools/generate-documentation` (`make gen-doc`). Output is committed, as today. Netlify does not need Go.
- Steps:
  1. Call cato as a library, with no exporter. It returns the documented config fields per file and struct. The generator writes them into the page front matter. The layout renders a table. (The `dir` shortcode goes away.)
  2. Parse all packages under `pkg/` and `internal/` with `go/parser`. Read the package doc comment, `README.md`, and `Register("name", ...)` calls in `init()`.
  3. Write one page per component.
  4. Write data files: plugin catalog, releases (from `changelog/`), commits per year (from `git log`), site stats.
  5. With `-contributors`: fetch contributors from the GitHub API into `data/contributors.json`. Without network, keep the old file.

### D3. Which packages get a page

A package gets a page if one of these is true:
- It registers a plugin (gRPC service, HTTP service, HTTP middleware, serverless service, driver of any family).
- It has a `README.md`.
- It has a config reference from cato.
- It is a plugin registry (the page lists its drivers).

Other packages with a doc comment appear in a "Libraries" list with their summary and a pkg.go.dev link. No page each: most are internal helpers.

### D4. Component page content

- Title, kind badge, Go import path, links to source and pkg.go.dev.
- The TOML section that enables it: `[grpc.services.<name>]`, `[http.services.<name>]`, `[http.middlewares.<name>]`, `[serverless.services.<name>]`, or `driver = "<name>"` for drivers.
- Package doc comment.
- `README.md`, with relative links rewritten to GitHub.
- Config reference: table of key, type, default, description, source line.
- For registries: table of drivers with summaries.
- For HTTP services: link to its tag in the Swagger UI, if the spec has that tag.
- Old `docs/autogenerated/...` URLs redirect with Hugo `aliases`.

### D5. Architecture diagram

- Inline SVG from a Hugo partial. Node positions in `data/architecture.yaml` (hand-placed, for a good layout).
- Layers: clients, HTTP front end, gateway, gRPC services, drivers, backends.
- Each node links to its component page. The partial fails the build if a target page does not exist.
- Hover shows the component summary, taken from the generated page.
- "Trace a request": select a scenario (WebDAV upload, create a share, OCM share). The edges on the path light up in order. Paths verified against the code.
- Same diagram, larger, on `/docs/concepts/architecture/`.

## Site map

```
/                               Home: hero, diagram, stats, features, deployments strip
/docs/                          Docs landing
/docs/getting-started/          Quick start: binary, source, Docker, first upload with the reva CLI
/docs/concepts/architecture/    Diagram, layers, request traces
/docs/concepts/configuration/   TOML structure, shared config, how plugins are chosen
/docs/components/               Generated. Grouped by kind, then by family
/docs/api/http/                 Swagger UI. Hugo fetches https://cernbox.cern.ch/openapi.json at build time (params.openapi) and publishes it on the site, so no CORS is needed. If the fetch fails, the page says so and the build continues.
/docs/api/grpc/                 CS3 APIs: links to buf.build and the proto repo
/docs/changelog/                Existing, restyled
/history/                       Timeline: milestones + releases + commits per year
/deployments/                   From data/deployments.yaml
/community/                     Contributors, how to contribute, chat, wiki
```

## Extras

- Search: Hugo writes a JSON index. Small JS search dialog (`/` or Ctrl-K).
- Dark mode: follows the system, with a toggle.
- Plugin catalog: one table of all drivers by family. Generated.
- Latest release and date in the header, from `VERSION` and `RELEASE_DATE`.
- "Edit this page" and "last updated" from git, on hand-written pages.
- Commits-per-year chart on the history page.

## Not in scope

- Talks and publications page: I have no verified data. Easy to add later as a data file.
- Deployments other than CERNBox: I have no verified data. The page is data-driven. The maintainers fill it in.
- Versioned docs.

## Status (2026-10-27)

All steps are done. Changes from the plan:

- D2: cato is not used. The generator reads `mapstructure` tags, field comments, and `ApplyDefaults` bodies itself. Cato covered 28 files; this covers every config struct. Only structs that the root `config` struct reaches are shown.
- D5: the hover text comes from `data/architecture.yaml`, because most packages have no doc comment. The traces are log in, upload, and share (not OCM). `#trace=<id>` starts a trace from a link.
- The OpenAPI generator was removed. The HTTP API page fetches the CERNBox document at build time. `HUGO_PARAMS_OPENAPI` overrides the URL.
- The quick start config needed `mount_id` on the storage and data providers and `public_url` on the data gateway. Tested with `cs3org/revad:v3.14.0` (podman): WebDAV PUT and GET, reva CLI login, ls, upload, download.

Validation results:

- `hugo --gc --minify`: one warning, expected until cernbox.cern.ch serves `/openapi.json`.
- Internal links: 0 broken. Hand-written external links: all 200.
- Swagger UI tested with a spec from a local revad with the `openapi` service.
- Screenshots: home, component, family, overview, quick start, API, history, community. Desktop and 390 px, light and dark.

## Facts checked while planning

- Docker images exist: `cs3org/revad:<version>`, with `-eos` and `-ceph` variants. Use them in the quick start.
- `tools/prepare-release` writes `docs/content/en/docs/changelog/<version>/_index.md`. Keep that path.
- `tests/revad/*.toml` holds a working multi-process setup. Base the quick start config on it.
